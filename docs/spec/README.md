# Spec

How the work is specified, ordered and verified. Read this, then `requirements.md`.

## Files

| File | Purpose |
| --- | --- |
| `requirements.md` | Disqualifying gates, then every requirement with milestone, kind, assertions, verify and status |
| `design-decisions.md` | Gaps in the statement and Figma, the decision, and the questions still open |
| `traceability.md` | Generated by `pnpm spec:check --write` |
| `/ARCHITECTURE.md` | Domain, REST contracts, purchase rules, session, real time, cache, mock layers |
| `../ENUNCIADO.md` | The statement (identical to the public README of the challenge repo) |

## Commands (the only validation set)

| Command | Use |
| --- | --- |
| `pnpm verify` | typecheck, lint, unit tests, build and `spec:check`. Run before saying a change is done |
| `pnpm test:unit` | Vitest, for pure rules (money, quote, idempotency, order state) |
| `pnpm test:e2e` | Playwright on the built app |
| `pnpm spec:check [--write]` | Checks requirements against tests; `--write` refreshes `traceability.md` |
| `pnpm dev` | Dev server with mocks (`.env` has `VITE_ENABLE_MOCKS=true`) |

Lighthouse is added at M0 and joins this table.

## Three separate things

1. **Gates (§11).** Six disqualifying criteria. A gate is closed only when every requirement that proves it is `done`. They are not work items.
2. **Required deliverables.** Every row with Kind `req`. Kind `opt` rows are improvements; they never block delivery and are cut first.
3. **Execution order.** Column M, below. It orders by dependency, not by importance.

## Milestones

Each milestone has an objective exit test. Do not start the next before the exit test passes, except for the per-screen work listed under "each".

| M | Goal | Exit test |
| --- | --- | --- |
| M0 | Proof and early deploy | The app is published; on that URL a `socket.io-client` connects through MSW and receives one event; a deep link refreshes; an initial Lighthouse measurement exists. If the socket proof fails, the fallback is decided here and recorded, before anything else |
| M1 | Foundations | Contracts in `src/api/types.ts` match `ARCHITECTURE.md`; mock layers (`db`, `services`, `handlers`, `socket`) exist with seeded ids, a clock, scenarios and reset; signup, login, session, logout and route guards work; wallets can be registered; money math is exact with unit tests |
| M2 | Purchase slice | As a seeded user: open a detail, add to cart, see the quote with a coupon, pick a wallet, confirm, see the pending screen move to a confirmed receipt through a real `order.updated`; refusal keeps the cart. One Playwright test runs this on desktop and mobile |
| M3 | Hardening | Timeout after creation recovers with the same key and one order; a price or stock change blocks a stale quote; reconnect and refresh recover a pending order; duplicate, old and late events change nothing; switching user shows no old data |
| M4 | Remaining required flows | Favorites with optimistic rollback, profile, avatar, password, wallet editing, mobile profile, wallets and confirmation, pagination and sort details |
| M5 | Completion sweep | The remaining scenarios, visual regression baselines, the 768 viewport, axe scan, and any `opt` rows time allows |
| M6 | Delivery | Lighthouse medians (3 runs), docs complete, clean-checkout run, hosting confirmed, and a smoke subset of the E2E suite passing on the public URL (DEL-10) |

**Rows marked `each`** (UI, accessibility, skeletons, out-of-scope controls) are not a milestone: they are part of finishing every screen.

### Done rule for a screen

A screen is not finished until all hold: matches its Figma frame (or the decided derivation); works at 390, 768 and 1440; has loading (skeleton), empty, error and success states; is operable by keyboard with focus handled in dialogs; announces mutations and live changes; has its tests. Lighthouse runs early on home and detail to catch problems, and the final medians are taken on the complete build at M6.

## Done rule for a requirement

- Verify `test`: status `done` only if every assertion in its **Accept** list has a test whose title names `ID#k` (for example `CART-6#2`). `pnpm spec:check` fails otherwise. A bare `ID` in a title proves nothing.
- Verify `manual`: a checklist entry in the PR or `ARCHITECTURE.md` with the date and what was checked.
- Verify `audit`: the report file in the repo.
- Verify `config`: the file or setting exists.
- CI or a local run must also be green, since the script cannot see a test fail.

## Evaluation traps

Each is a way to pass locally and still lose. Where the plan answers it:

| Trap | Why it fails | Answer | Proof |
| --- | --- | --- | --- |
| Visual tests pass | Baselines made from a wrong screen keep the error | Compare each screen with its Figma frame before creating or accepting a baseline; record it | UI-1, TEST-3 |
| Order created, receipt shown | Pending is not confirmed | Receipt only from a read that returns confirmed with a receipt | ORD-3, DQ-3 |
| Socket drop erases the purchase | Refresh and reconnect only seem to work | Order progression is persisted with a due time and settles without the socket or the screen | MOCK-12, ORD-2, RT-9 |
| Page guards isolate users | A direct call still reads another user's order | Ownership checks in every handler | AUTH-12, DQ-4 |
| Disabling the button prevents duplicates | Timeout, refresh and resend bypass it | Idempotency and one-pending-order rules in the API, with a persisted key | CHK-5, ORD-7, ORD-8, ORD-9 |
| Reset restores the NFTs | Old sessions, orders, keys and queued events leak into the next run | Reset clears all state and drops older events by generation | MOCK-3, MOCK-13 |
| Scenarios are hidden in tests | The evaluator cannot cause the failures | `?scenario=` on the public URL, a visible reset, a README table | MOCK-14, DEL-3 |
| Local tests are green | The deploy is another environment | A smoke subset of E2E runs on the public URL | DEL-10, DEL-2 |

## Rules

1. Tests first for new behavior: write it, watch it fail, then implement.
2. Anything the statement or Figma leaves open goes to `design-decisions.md` before it is coded.
3. Candidates' Figma comments are hints, not requirements. A comment becomes work only if the statement or the frame supports it.
4. Do not flatten desktop and mobile when the Figma draws them differently on purpose.
5. A documented deviation from the Figma still costs fidelity points. Prefer matching the frame.
6. Cuts are listed under "Not doing", never silent.
7. Ask before committing: files, message, author.
8. Visual baselines are created only after the screen was compared with its Figma frame.

## Glossary

Domain terms (NFT, edition, unit, token id, quote, order, receipt) are defined in `ARCHITECTURE.md` §1.

## Assumptions

- The UI is Portuguese (pt-BR) to match the Figma; code, comments, commits and docs are English.
- Chromium only for tests.
- No real backend; the statement forbids depending on one (§12). The deployed build ships the mocks (§6).

## Not doing

| Item | Why |
| --- | --- |
| Editorial, support, activity, watchlist, offers and downloads pages | Out of scope (§3). Entry points are inert and labelled "Em breve" |
| "Esqueceu a senha?" and "Ou continue com" (social login) | Not in the required flows; shown disabled |
| Real blockchain, wallet extensions, payment gateways | Out of scope (§1) |
| Light theme | The Figma has only a dark theme |
| Browsers other than Chromium | §9 asks for Chromium |
